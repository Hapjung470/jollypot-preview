전달의 핵심 — 왜 일부만 개발하나

졸리팟 전체 기획을 한꺼번에 개발하지 않습니다. 전체 중 일부분만 린하게 먼저 개발하고, 실제 사용자와 핏(fit)을 맞춰본 뒤, 검증된 방향으로 추가 개발을 지속하는 방식입니다.

그래서 이번 전달 범위는 “돌려보며 검증할 최소 한 바퀴”에 필요한 화면·기능으로 한정했습니다. 전달드린 프로토타입 URL에는 전체 기획의 후반부 작업(스크랩북 SNS·요리모드·요리후기 등)이 함께 보일 수 있으나, 이번 개발 범위가 아닙니다. 혼선이 없도록 본 문서 하단에 ‘추후 개발’ 영역을 명확히 분리해 표기했습니다.

섹션 여백·구분 규칙공통

냉장고 관리 (신규) — 수동 중심 + 📷 사진 보조

수동 입력이 기본(spine)이고, 타이핑을 줄여주는 📷 사진 보조(‘보이는 것만’)가 더해졌습니다. 냉장고 ‘전체를 AI로 스캔’하는 방식이 아니라, 앞줄·포장식품만 빠르게 담는 보조입니다. 진입점은 홈(01번)과 연결됩니다.

⚑ 방식 — ‘전체 AI 스캔’은 폐기, ‘보이는 것만 보조’로 안착
2샷 촬영·스캔결과·스캔실패 화면, AI 비전 모델(Gemini/벤더) 채택 이슈는 제거. 대신 사진은 또렷이 보이는 것만 인식해 수동 추가 시트에 미리 채워주는 보조로 정리됐습니다(반찬통·안쪽은 처음부터 비대상).

📷 사진 보조 — 핵심 동작 규칙 (precision 우선)
고신뢰=실선·기본 포함(✕로 제외) / 저신뢰=점선 “이거 맞나요?”·기본 제외(‘네, 맞아요’ 눌러야 담김). 담기 카운트=확실+확인분만 — 보증 없는 추측은 저장 안 함. 모델 목표는 recall보다 precision. 위치는 추정→결과 행에서 토글 교정. ‘0개 인식’도 실패가 아님(직접 추가로 연결). 별도 ‘스캔 실패’ 화면 없음.

⚑ 결정 필요 — 구현 포인트
① 레시피 매칭 로직(보유 재료 ↔ 레시피 재료 정합 → 부족분 산출) — 냉장고의 실질 백엔드. ② ‘자주 넣는 재료’ 기본 사전(칩 세트) 정의. ③ 사진 인식 합격선 = precision 기준(애매하면 저신뢰로 흘려보내 사용자 확정). 모델은 레시피 추출용 Gemini Flash 재활용 전제 → 새 비전 벤더 결정 없음. ※ ‘빈 상태 스타일’은 인라인 빠른추가로 확정(2안 중 택1 완료).

05 네이티브 확장 · 앱 패키징 개별 산정 · 재패키징 1회

앱 패키징 — 푸시 & 딥링크 (네이티브)

하이브리드 앱에 푸시 알림과 딥링크를 붙이는 네이티브 작업입니다. 앞의 4개(웹 범위)와 달리 스토어 재심사가 필요해 각각 개별 산정으로 분리합니다. 두 건 모두 네이티브를 건드리므로 재패키징·스토어 제출은 1회로 묶어 중복비용을 방지합니다.

5-A. 푸시 알림개별 산정
만드는 방식 — 인프라는 "얹기"
발송 인프라는 FCM/OneSignal 등 SaaS를 얹습니다(앱 푸시 발송은 무료). 개발사 산출물은 ①SDK 심기(네이티브) ②딥링크 라우팅(클릭→앱 화면) ③샵바이 회원·구매 데이터를 세그먼트로 연동 — 이 3가지로 한정합니다. 발송·이미지·예약·통계 UI는 SaaS 대시보드가 대체합니다.
딥링크 랜딩(P0)이미지 푸시(P0)예약 발송(P0) 세그먼트 T2(P0)수신동의·야간제한(법적·P0)발송 통계(SaaS대체) 개인화 토큰(고효과)자동화 1~2개·장바구니이탈/재입고(고효과) A/B 테스트 (2차) 복잡 세그먼트·RFM (2차) 리치버튼·인앱메시지 (2차)
운영 방식: 발송·예약·통계는 운영자가 SaaS 대시보드에서 직접 처리합니다(개발 최소). 어드민에 발송화면을 통합하는 방식은 이번 범위가 아닙니다.
5-B. 딥링크 (유니버설 + 디퍼드)개별 산정
구조 — 규칙표 한 번 → 모든 링크 자동 딥링크
상품마다 수작업이 아니라 URL 규칙표(route map)를 코드에 한 번 심습니다(예: /product/:id · /recipe/:id · /event/:id). 이후 그 패턴을 따르는 모든 표준 URL이 자동으로 딥링크로 작동합니다. 유니버설/앱링크(https 링크가 앱을 엶) 네이티브 등록 + 도메인 인증파일(assetlinks.json / apple-app-site-association) 호스팅, 디퍼드(미설치→설치 후 목적지 유지)는 SDK(Branch 등)로 처리합니다.
어드민에 붙는 것 — "딥링크 생성기" 화면 1개 (UTM 태깅 전용)
딥링크 전환은 URL 규칙표가 자동으로 처리하므로, 이 화면이 하는 일은 어느 매체로 내보냈는지 UTM 태그를 남기는 것뿐입니다. 어드민에 새 메뉴 [딥링크 생성기]를 붙입니다. 흐름 3단계: ①링크 붙여넣기(샵바이·졸리팟 URL을 그대로 붙여넣으면 대상 유형을 패턴으로 자동 인식) → ②캠페인 태그(마케팅 매체 utm_source · 자사 채널 utm_medium · 캠페인명 utm_campaign — 태그 종류는 ⚙ 태그 관리에서 운영자가 추가·삭제) → ③생성된 링크 + 복사. 운영자는 이 링크를 푸시·카톡·인스타·문자에 붙여넣습니다.
어드민 — 딥링크 생성기 열기 →
미설치 유저 폴백 — 상단 배너 한 줄
앱 미설치 유저가 딥링크를 열면 웹 페이지를 그대로 보여주고, 페이지 상단에 앱 배너 한 줄(44px)만 얹습니다. 콘텐츠를 가리지 않습니다. 구성: 앱 아이콘 + "졸리팟 앱에서 보기" + [열기] 버튼 + [✕] 닫기. [열기] → 설치자는 앱이 열리고, 미설치자는 스토어로. ✕ 닫으면 24시간 미노출. iOS는 OS 기본 Smart App Banner(apple-itunes-app 메타태그 1줄)로 대체 가능. 결제·주문서 화면에서는 표시하지 않습니다.
순서: 푸시 클릭→이동이 딥링크에 의존하므로 딥링크(규칙표·네이티브등록)를 먼저, 푸시가 이를 가져다 씁니다.
공통 전제 — 재패키징 1회 + 계정·인증서 이관
푸시·딥링크 모두 네이티브라 재패키징·스토어 제출은 1회로 묶습니다(양쪽 산정에 중복 계상 금지). 전제 조건: 긱스튜디오로부터 keystore(안드로이드 서명키)·APNs 인증서(iOS)·Firebase/스토어 콘솔 계정 이관 — 이것이 없으면 재패키징·앱링크 인증이 물리적으로 불가합니다.

주문하기 — 구매 플로우 전체 (옵션 선택 → 주문서 → 결제)

기존 샵바이 기본 스킨을 디자인 가이드 v2.0.4 기준으로 전면 재설계했습니다. 구매하기 → 옵션 선택 → 주문서 → 결제수단 → 결제 실패·중단까지 구매 동선 전체가 이번 범위입니다.

6-A. 구매 플로우purchase-flow · v10 열기 →
상품상세 [구매하기]→옵션1 선택→옵션2 선택→선택완료(수량·금액)→주문하기
바텀시트 2단 옵션 품절 옵션 비활성 노출 구매하기 조건부 활성
단계 규칙
· 옵션 축의 이름·개수는 상품 데이터에서 렌더링한다(하드코딩 금지) — 셀렉트 문구는 {파트너 설정 옵션명} 선택하기, 미설정 시 "선택1/선택2"로 폴백. 안내·가이드 문구에는 옵션명을 쓰지 않는다
· 옵션 경우의 수 8종 전부 대응(v10): 필수1 / 필수2 / 필수3 / 필수2+선택1 / 텍스트2 / 추가구성 / 복합 / 옵션없음
· ★ 선택옵션은 "+N원"이 아니라 절대가로 표기 — 샵바이 선택옵션 가격은 본품가+addPrice이고 addPrice에 음수가 들어간다(실측: 본품 6,700 · 리필잉크 addPrice −4,200 → 2,500원). 증분 표기하면 "+ −4,200원"이 된다
· 입력형(텍스트) 옵션: 필수/선택 구분 · 글자수 실시간 카운터 · 초과 시 결제 차단 · 재고와 무관하므로 순서 강제 없이 맨 뒤
· 추가구성상품: 본품 옵션 완료 후에만 노출(본품 없는 주문 방지) · 금액 소계 분리 · 썸네일 없이 [✓] 상품명 … 가격 한 줄(시트 전체가 텍스트 기반이라 이미지가 리듬을 깬다 · 파트너 이미지 품질 의존도 제거) · 서버 API 미구현(실호출 시 무시)이라 어드민 수동 등록만 가능 — 이번 범위 포함 여부 결정 필요
· 축 개수 3가지 모두 처리: 2단(순서 강제) / 1단(두 번째 셀렉트 자체를 렌더링하지 않고 선택 즉시 완료) / 없음(시트를 열지 않고 바로 주문서로) — 1단 상품에 빈 2번째 셀렉트가 뜨면 구매가 막힌 것처럼 보인다
· 옵션2는 옵션1 선택 전까지 비활성(회색) — 순서를 강제해 잘못된 조합 방지. 옵션1 선택 시 옵션2 자동 펼침
· 옵션 행 구성 = 이름 + 추가금(+N원) + [주문많음] 배지 · 품절 상태만 부가 표기
· 도착일은 표기하지 않는다 — 파트너 배송이라 출고·배송 리드타임을 통제할 수 없다. 대신 배송비·무료배송 임계·출고 소요일(파트너 설정값)만 노출하며, 파트너가 출고일을 미설정한 상품은 문구 자체를 노출하지 않는다(기본값 임의 채움 금지)
· 품절 옵션은 숨기지 않고 흐리게 노출 — 있는 줄 알고 찾는 유저의 확인 비용 제거
· 구매하기는 옵션 미선택 시 비활성 + 버튼 위 캡션으로 이유 상시 안내(누른 뒤 토스트 방식보다 마찰 적음)
· 선택 완료 카드 = 조합명 / 수량 스테퍼 / 금액 / ✕ · ✕ 또는 카드 탭 시 옵션1부터 재선택
· 시트 높이는 내용이 아니라 고정(상단 여백 = 앱바 높이, top:56px; bottom:0) — 옵션이 2개뿐이어도 시트는 항상 높다. 스크롤은 시트 내부에서만, 요약·CTA는 하단 고정
· 셀렉트 + 옵션 목록은 하나의 테두리 그룹(내부는 1px 구분선만) — 각각 테두리를 주면 이중 테두리·어긋남 발생
· 시트 상단에 제목 + ✕ 닫기 · 시트 표시 중 배경 스크롤 잠금(스크롤바 폭 보정 동반)
시트 금액 표기: 쿠폰은 시트에서 계산하지 않는다("주문서에서 적용"만 표기) — 시트와 주문서 금액이 어긋나면 신뢰가 깨진다. 배송비는 예상 결제금액에 합산하지 않고 아래 별도 표기.
구현: 샵바이 선택옵션 2단(multiLevelOptions) · 옵션가 = 본품가 + addPrice · 조합별 재고/품절 반영 · 조합 다중 선택은 이번 범위 제외(카드 리스트로 확장 가능한 구조로만 설계)

· 주문자 정보 섹션 없음 — 회원 정보를 사용합니다(기존 주문서의 재입력 폼 제거).
결제수단 순서: 퀵계좌이체(히어로·기본 선택, 0.5% 즉시 할인) → 신용/체크카드 → [가상계좌 ㅣ 간편결제(네이버페이)] 2단.
· 실시간 계좌이체 제외 · 수단 버튼 높이 52px 동일(위계는 폭으로만) · "다음에도 사용" 체크박스 기본 ON
결제 실패·중단 상태 5종: ①수단 거절(시트) ②결제 중단(시트) ③결과 확인 중(전체화면) ④결제 중 품절(전체화면) ⑤시스템 오류(시트).
· ③은 재시도 버튼을 제공하지 않습니다 — 중복 결제의 주 원인. 폴링+웹훅 병행, 동일 주문 재결제 차단(멱등키) 필수
· PG 응답코드 → 상태 5종 매핑표 필요, 미분류 코드는 ⑤로 폴백
구현 함정 2가지(실측 반영): ①화면 어느 요소든 가로로 넘치면 position:fixed 하단바·모달 폭까지 함께 틀어집니다(실측 12px) — QA에 scrollWidth === clientWidth 체크 포함 ②모달·바텀시트로 배경 스크롤을 잠글 때 스크롤바 폭 보정을 함께 처리(미보정 시 PC 웹에서 15px 흔들림)
받을 것: 주문서 1화면 + 결제 실패·중단 5종 구현 범위. 결제 연동 자체(PG)는 기존 샵바이 연동 유지 전제.
6-C. 절약 금액 산식 — 온라인 정가 기준확정
산식
아껴요 = (온라인 정가 − 판매가) + 쿠폰 할인 + 적립금 사용
= 상품 할인 + 쿠폰 할인 + 적립금 사용 · 배송비는 포함하지 않는다
예시: 정가 14,000 − 판매가 9,500 = 상품 할인 4,500 · 쿠폰 2,700 · 적립금 0 → 아껴요 7,200원
총 결제 = 14,000 − 4,500 − 2,700 − 0 + 배송비 3,000 = 9,800원
결제 금액 블록 표기 순서(확정): 총 상품 금액(정가) → 상품 할인(−) → 쿠폰 할인(−) → 적립금 사용(−) → 총 배송비(+) → 총 결제 금액.
· 빼는 항목을 모두 처리한 뒤 더하는 항목을 마지막에 둬야 위에서 아래로 읽으며 계산이 맞아떨어집니다.
· 총 상품 금액을 판매가로 시작하면 "아껴요"의 상품 할인분이 화면 어디에도 없어 숫자의 근거가 사라집니다.
가드(필수 구현)
· 정가 ≤ 판매가 → 상품 할인 = 0 · 정가 미설정 상품 → 판매가를 정가로 간주(할인 0)
· 아껴요 합계 ≤ 0이면 스트립 미노출 + 이때만 하단 바 상단 1px 구분선 노출
· 배송비는 절대 합산 금지(무료배송은 별도 배지) — 섞으면 "무료배송 상품이 항상 더 이득"으로 왜곡됩니다
⚑ 법무·운영 확인: 정가는 "종전 거래가격"이어야 합니다(표시광고법). 판매 이력 없는 가공 정가로 할인율을 표기하면 부당 표시가 될 수 있습니다. 정가는 파트너가 입력하는 값이므로, 그 값으로 "아껴요"를 계산하는 순간 표기 책임이 우리에게 옮겨옵니다 — 파트너 어드민의 정가 입력 기준 안내 + 입점계약 표기 책임 조항 확인 필요.
